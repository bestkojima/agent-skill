# 对话示例

用于校准讨论粒度与交付边界，不照抄成固定题库。示例中的平台、算法、任务规模和排版均为当次选择。

## 示例一：讨论进程调度，再按反馈收敛

### 只给知识点

用户：给我出一道进程调度的 C++ 练习题。

助手：可以设计成两种小 demo：

- **进程调度演示器**：让几个模拟进程轮流获得 CPU，观察任务执行、状态变化和进度恢复，适合先理解调度过程。
- **调度策略对比实验**：同一组任务分别使用 FCFS 和时间片轮转，比较执行过程与等待情况，需要理解两种策略。

如果刚学完基本概念，我建议先做演示器。你更希望学生看清调度过程，还是比较不同策略？

这一轮等待用户选择，不在问题后附完整题面。

### 用户继续比较

用户：第一种会不会太简单？

助手：第一种也可以要求进程执行真实的分步任务，在切换后保存并恢复进度，同时展示状态变化。学生需要把调度过程实现出来。第二种则增加策略对比和结果解释。你希望先把第一种做扎实，还是增加策略对比？

这个问题尚未选定方向，继续讨论即可。

### 用户选定后形成题面

用户：做第一种，用时间片轮转，全部进程一开始就绪，只做模拟。学生会 C++ 基础，只要题目。

助手：**练习题：用 C++ 实现进程调度演示器**

实现一个单核调度小 demo，观察模拟进程如何获得 CPU、执行任务、用完时间片以及从保存的进度继续执行。

需要实现：

1. 保存每个模拟进程的编号、状态、任务总步数、已完成步数和当前结果。
2. 让进程执行可分步完成的任务，例如依次累加 1 到 N；只有获得模拟 CPU 才能推进一步。
3. 按时间片轮转调度。所有进程初始就绪，按创建顺序参与；一个模拟时间单位执行一步，时间片是正整数。
4. 任务未完成且时间片耗尽时保存进度，进程转为就绪并等待下一轮。提前完成则转为结束，立即选择下一进程。
5. 根据实际执行输出日志：谁在运行、执行到哪一步、为何切换、最终任务结果。全部完成后结束程序。

环境与范围：普通 C++ 控制台程序即可，可自行使用标准库。使用程序内模拟时间，忽略切换耗时，不加入真实线程、I/O 阻塞或运行中新到达进程。

演示：创建分别需要 5、3、1 步的任务，将时间片设为 2，再改为 1 和 4。观察切换频率和完成顺序，输出格式自行设计。

完成标准：每个任务步骤连续且恰好执行一次，结果与完整累加一致；同一时刻最多一个进程运行；已结束进程不再调度；单个剩余进程仍能执行完毕；日志与实际状态对应。

### 降低外围实现难度

用户：学生还没学过类，能不能简单点？

助手：可以保留同一个调度目标，用结构体保存进程信息，用普通函数组织执行和调度，不要求类或继承。任务先统一为逐步累加，仍保留时间片切换、进度保存和状态变化这三个核心要求。

按用户需要给出修订后的相关部分或完整题面，不重新询问已经确定的算法与实践类型。

### 只给起步提示

用户：只提示一下怎么开始，不要答案。

助手：先想清楚，一个进程切换出去之后，哪些信息必须留下来才能继续执行？可以先让一个任务分两次调用推进，确认第二次能从上次的位置继续，再考虑多个任务轮流执行。

停在这一层，不补上完整调度循环、全部数据结构或参考代码。

## 示例二：明确要求，直接设计真实系统实验

用户：做 Linux 父子进程管道通信 demo，父进程发消息，子进程回结果，直接出题，只要题目。

助手：**练习题：父子进程的请求与响应**

使用 C++ 在 Linux 上创建一个子进程，让父进程发送一条字符串，子进程计算其字节数并返回，父进程打印结果并回收子进程。

本题用两条管道承载两个通信方向。父进程负责输入，子进程不读取终端。一次运行只处理一条不含换行的 ASCII 字符串，长度为 0 到 100 字节；请求和响应均以换行结束，响应是十进制字节数。双方按协议识别完整消息，不能假设一次读取或写入必然完成全部数据。

要求关闭各自不使用的管道端，处理必要的系统调用失败，在通信结束后关闭剩余端并回收子进程。正常演示中父子双方完成约定的数据交换后退出；一方提前关闭导致消息不完整时，报告通信失败并结束，避免无限等待。

演示空字符串、普通英文和包含空格的文本，确认长度正确；让子进程在收到请求前退出，验证父进程能检测通信失败并清理资源。

完成标准：数据确实通过管道跨进程传递；正常与失败路径均能结束；父进程取得并报告子进程退出状态。不要求父子日志按固定顺序交错。

这里已有目标、平台与直接出题要求，不再先询问“模拟还是实际通信”，也不附完整实现。实现时涉及的信号与读写错误规则需按实际平台核实。

## 示例三：学生不会 Socket，讨论合适的实验

用户：学生还不会 Socket，想练 TCP 消息边界。

助手：可以先做一个分块数据驱动的消息解码器：把同一段字节流分几次传入，观察程序怎样保留不完整的数据，再还原完整消息。它练的是应用层消息解析，暂时不需要建立真实连接。

可以从一种带长度字段的协议入手，也可以比较长度字段和分隔符两种消息边界方案。刚接触这个知识点时，我建议先做好一种协议。你想先掌握分块解析过程，还是同时比较两种协议？

用户：就第一种，长度字段，不要比较，直接出题。

助手随后应定义一种明确的长度编码、正文范围和结束约定，让学生实现增量解析。题目通过多种分块方式验证消息内容与顺序相同；不要要求某次真实网络读取必须产生“半包”，也不要变成只打印预设消息的程序。

## 示例四：授权自行选择与回答其他类型请求

用户：给我一个条件变量练习，具体场景你来定，直接出题。

直接选择合适的小场景，例如固定数量任务的生产与消费。题面应包含条件状态、任务不丢不重、停止信号和线程回收；说明采用的环境与前置条件。无需再次询问候选方向，不默认给答案。

用户：要求多个线程每次都按某个固定顺序打印。

结合上下文确定是否已指定顺序。若尚未确定，可讨论一次性依次执行还是循环轮流执行；正式题面应要求显式同步建立顺序，并把启动先后或 sleep 排除为顺序保证。只要具体要求足够，就直接完善题面。

用户：补充参考答案。

沿用当前题面提供代码和解释，在可用环境中验证。若无法在目标平台运行，说明限制，不声称已测试；不另换一个更易实现的题目。
