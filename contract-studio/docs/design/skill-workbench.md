# 以功能节点组织 AI 开发

状态：设计与验收范围已确认。日期：2026-11-13。当前使用方式见[项目说明](../../README.md)。

## 用户要完成的工作

在功能图里提出或修改功能，通过节点属性说明需求，让 AI 找到相关实现并完成开发；再回到工作台操作功能，查看结果、代码和测试，判断需求是否落实。

框架承担节点编辑、属性保存、上下文生成、实现绑定、需求索引和证据展示；Skill 保持精简，引导 Agent 使用这些既有能力。Skill 验收关注 [Agent 在框架内完成节点任务](../skill-evaluation.md)的过程。计算器与平均值用于演示框架，具体业务规则留在示例中。

- 计算器统一为一个示例，保留两数四则、多数字求和和带优先级的混合运算。

## 节点属性：编辑契约，查看证据

以下为本轮实施与验收规格。

### 身份与结构

- 稳定节点 ID、名称、节点类型、父节点。类型区分功能组、处理步骤与界面；功能组可继续添加子节点。
- 父子关系表示包含；连线表示数据传递或业务依赖，必要时记录分支条件。移动位置、折叠和缩放属于展示设置。
- 一个节点可关联多条需求，一条需求也可由多个节点共同落实。兼容旧数据的单条关联，保留已有需求 ID。

### 重要性

节点属性 `importance` 使用三个等级，按业务职责选择：

- `core`：**核心逻辑**，决定主要行为与结果的规则或处理，使用紫色。
- `key`：**关键逻辑**，保障核心逻辑正确运行的校验、依赖处理或关键分支，使用琥珀色。
- `normal`：**普通组成逻辑**，承担一般组装和辅助职责，使用蓝灰色。

新节点及缺少此字段的旧节点默认为 `normal`。等级独立于节点类型、父子结构和执行状态，画布同时使用颜色与文字标识，侧栏编辑后随图保存，并进入节点说明及开发任务。仅调整重要性不改变需求确认、运行绑定或测试证据的有效性。

重点视图突出核心与关键逻辑，淡化普通组成逻辑并保留依赖关系。节点聚焦以当前节点及直接关联为阅读范围，保留所属功能组的上下文；总览用于返回全图。这两项属于临时视图状态，不写入行为契约。

### 行为契约

- 职责：这个节点完成什么。
- 输入与输出：字段、数据类型、单位（如有）、约束和示例；说明文字与结构化契约并存。
- 处理规则：业务规则、依赖步骤及必要的顺序要求。
- 异常：触发条件、错误标识、用户可见反馈。
- 验收条件：带稳定标识的输入、预期结果及可观察行为，供测试逐项对应。

需求正文与需求级验收条件只在需求源中维护，节点以关联读取并显示；节点特有的输入输出和处理规则属于节点规格。侧栏编辑关联需求时保存到该需求源，避免将正文复制到每个节点。

### 实现与前端对应

- 能力 ID：连接实际运行入口与功能节点的稳定引用；仅可绑定项目中受信任、已登记的能力。
- 后端实现：入口及相关函数，使用文件、符号和解析出的定位信息；行号是导航结果，函数身份不随行号变化。
- 前端入口：实际组件或操作入口及其输入、成功结果、失败反馈。
- 测试关联：测试用例与验收条件对应；允许多个测试覆盖一个功能。

实现与测试位置由受支持的索引结果解析；缺项显示待接入。文档中的关联不自动授予运行权限，画布也不接受任意 Shell 命令。

功能接入统一使用可信登记：来源文件、别名、路由、实现符号、前端入口及测试信息由功能模块声明，框架消费声明。业务组件放在相应前端模块中；框架宿主负责图和节点面板，避免为每项业务追加分支。旧入口与浏览器草稿身份随登记保留。

### 状态与证据

需求确认、实现接入、测试结果分开呈现。用户确认的是需求内容；实现链接存在只说明定位成功。现有确认记录仅覆盖标题和描述，保留其修订、时间和原文快照；新增的验收条件需要取得对应确认，旧记录不能被扩大解释为整份节点契约均已确认。运行记录显示真实输入输出、错误、步骤和耗时；测试结果引用实际执行报告。

新节点可先保存为草稿。没有执行绑定时显示“待实现”，相应运行入口不可用；具有实际入口后才开放运行。需求行为或相关代码变化会使旧证据显示待复验，移动节点位置不改变需求确认。运行记录、工具版本和历史不塞入功能图，使用独立报告、项目配置与 Git。

节点描述文档由上述源数据和索引派生。框架的节点上下文接口同时生成结构化数据、说明和开发任务，侧栏与 Agent 使用同一生产路径。保存状态的读取和画布草稿的只读预览分开；预览使用已保存需求，并说明行为差异对测试证据的影响。导出的说明是快照，接手时核对当前源数据。

## 函数划分：按职责拆，保留现有入口

- **输入处理**负责文本解析与格式反馈，产出后端约定的数据；前端不另算一份业务结果。
- **业务校验**决定可接受输入，后端执行最终校验。通用数字解析可以复用，各功能的数量约束保持独立。
- **纯计算**负责累加、计数、均值等规则，返回数值和步骤；不读取 HTTP、界面状态或编辑器配置。
- **流程入口**组织校验与计算，汇集 trace，返回一致的成功或失败结果。
- **界面组件**负责输入、请求状态、结果、错误及步骤呈现；图高亮来自本次运行记录。

共享函数按真实职责复用，不按每个节点复制。已有函数、API 和源码标记保持可用；比如新增平均值允许单个数字，不得把既有求和“至少 3 个数字”的约束放宽。

## 前后端对应：按功能验收

每项用户能力沿同一条链核对：需求 ID → 功能节点 → 后端入口 → 前端操作 → 验收用例与结果。

“后端已实现、前端没有入口”“前端有操作、没有真实后端”“运行成功、没有验收证据”分别呈现缺口。输入校验、成功结果、错误反馈和过程展示均应对应实际后端行为。辅助函数只需能在实现详情定位。

同一能力在统一界面中提供入口；计算器继续共用输入与键盘，增加平均值模式及示例。功能组可以汇总子节点状态，但只有实际绑定的入口可运行，不能将前端派生的高亮冒充后端执行步骤。

## Sphinx-Needs、CodeLinks、ubCode 的职责

Codex 根据自然语言整理结构化需求；Sphinx-Needs 解析需求条目、类型与关系。CodeLinks 读取源码标记并建立引用。ubCode 提供兼容的索引、诊断和 CLI/MCP 查询；React Flow 显示这些数据并提供编辑与运行入口。

官方依据：[Sphinx-Needs](https://sphinx-needs.readthedocs.io/en/latest/)、[needs.json 构建](https://sphinx-needs.readthedocs.io/en/latest/builders.html)、[CodeLinks](https://codelinks.useblocks.com/)、[ubCode 与 Sphinx 集成](https://ubcode.useblocks.com/paths/sphinx.html)、[ubCode MCP](https://ubcode.useblocks.com/features/mcp/index.html)。ubCode 的项目 MCP 工具需要适用的项目许可；工具安装和许可可用性须分别确认。

### 已确认的接入方案

框架保留现有 JSON 作为可编辑源，保留需求 ID、确认记录、旧接口及浏览器草稿。保存后生成 RST，实际运行 Sphinx-Needs 与 CodeLinks，再由后端将构建结果整理为前端和 Codex 共用的追踪视图。来源适配由框架接入层处理，Skill 使用既定入口。

```text
项目需求与节点源 → 派生 RST → Sphinx-Needs + CodeLinks → 构建索引
                                                        ↓
                                                工作台 / Codex
已保存的 RST 与源码 → ubCode 索引、诊断、CLI/MCP 查询（接入后）
真实业务运行与测试 → 独立执行证据 → 工作台节点
```

每次索引显示来源、对应源修订和构建结果。源已保存但构建失败时，编辑状态保持已保存，追踪状态显示构建失败或过期；不得用旧索引冒充当前结果。原文、画布草稿、索引和执行证据保持可区分。

CodeLinks 产物中的项目别名先按配置解析为仓库内受限路径，再用于源码预览和编辑器导航；所有入口使用一致的引用解析。当前配置未覆盖 Java/PHP，迁移时必须保留其现有引用能力并明确实际来源，或补齐正式索引支持，不能悄悄丢失旧功能。源文件扫描可作为显式标注的兼容来源，不得冒充 Sphinx 或 ubCode 构建结果。

本轮必须实际接通 Sphinx-Needs + CodeLinks。ubCode 在工具及适用许可就绪后接入，工作台明确显示其接入状态；基础开发闭环保持可独立使用。

## 平均值：示例项目的贯通测试题

业务规则：接受一个或多个有限数字，支持负数、小数和零；空列表、空项、非法数字以及计算中超出有限数值范围时明确报错，不丢弃非法项。沿用现有 JavaScript 浮点数约定。

功能图位于“计算 → 平均值”，展开后展示校验、累加与计数、计算均值；结果区显示数量、总和、平均值和真实步骤。复用数字处理与累加逻辑，保持求和至少 3 个数的既有行为。

验收样例：

- `1, 2, 3` → 数量 3，总和 6，平均值 2。
- `1` 至 `20` → 数量 20，总和 210，平均值 10.5；显示 20 次累加及除以 20 的过程。
- 单值 `7` → 平均值 7；`-2, 0, 5` → 平均值 1；`0.5, 1.5` → 平均值 1。
- 空输入、空项、非法值、非有限值 → 错误反馈；没有伪造的成功结果，保留实际产生的失败步骤。

示例项目的验证顺序：

1. 在图中添加节点，侧栏填写契约并关联需求，保存后重新打开仍保留。
2. 生成节点说明与供当前 Codex 读取的开发上下文，包含需求、函数关联、前端缺口和验收条件。
3. Codex 实现真实后端、前端入口与测试，更新代码标记；工作台重新索引并展示关联。
4. 通过实际 Sphinx-Needs 与 CodeLinks 构建验证平均值需求、节点及代码关系，显示索引状态和实际来源。
5. 在前端运行成功与失败样例，核对 API 结果、过程、图高亮和代码/测试定位，并取得实际测试证据。
